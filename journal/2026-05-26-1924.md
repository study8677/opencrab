# 进化提速诊断航次 🧱⏱️

**意图**：用 friction + throughput + parallelpilot 回放近 30 次自改，先量「慢在哪」，再谈提速——不靠砍验证作弊。

## 怎么量的（观测者，只读不写）

- `friction.jsonl` 尚不存在：摩擦账本从没被记过，所以 `friction --top` 无料可报。**第一个发现：最大的摩擦其实是「没人记摩擦」**——慢点全靠事后从 audit 反推，而不是当场登记。
- 改从 `state/audit/2026-05-26.jsonl` 回放 tick 事件（throughput 的同一数据源），按 throughput.py 的分段口径拆每拍四段：
  - think = `tick_start → intent`
  - work  = `intent → act`
  - verify/commit = `act → tick_done`
  - cooldown = `tick_done → 下一拍 tick_start`

## 分段实测（近 18 拍，18:54–19:24）

| 段 | 19:00 之前 | 19:00 之后 |
|---|---|---|
| think | ~7–9s（稳） | ~7–9s（稳） |
| **work（intent→act）** | **~2–6s** | **~90–149s** 🔴 |
| verify/commit | ~0.03s | ~0.03–8s |
| **cooldown（done→start）** | **恰好 30.0s** | **恰好 30.0s** |

两个等待点，按量级排序：

1. **work 段在 19:00 一刀切式暴涨**：tick `19:00:05` 起，`intent→act` 从 ~5s 跳到 ~120s（20–25×），此后每拍稳定 90–149s。这不是噪声，是制度性回归——某个改动把「干活」段拖长了一个量级，是当前最大的单一杠杆。
2. **每拍固定 30.0s 冷却**（done→下一 start，分秒不差）：单看是常数，但在 19:00 之前 work 仅 ~5s 的轻拍里，这 30s 冷却才是真正的吞吐瓶颈——30 拍累计 15 分钟纯空等。

## 并行验证：设计了，但这一拍没能实跑

`parallelpilot --run` 需要执行子进程；本航次 python 执行被权限闸门挡下（预算也见底），**没有伪造跑批结果**。把待验证集如实入队留给下一拍落地：

```
parallelpilot --add "回归 throughput 分段口径" --kind verify --cmd "python3 throughput.py --days 2 --slow 5" --reads throughput.py
parallelpilot --add "回归 friction 账本读写"   --kind verify --cmd "python3 friction.py --since 30 --json" --reads friction.py
parallelpilot --add "并行自检无写冲突"          --kind verify --reads state/audit/2026-05-26.jsonl
parallelpilot --run --gate 1.0
```

依据：这三条 verify 互不写盘、读集不交，正是 parallelpilot 该并行的形态——若 work 段那 120s 里有串行验证命令，搬进并行航次能直接砍掉墙钟。

## 结论 / 下一拍

- **先查 19:00 那次改动**：定位让 work 段从 5s 涨到 120s 的提交，确认是「活变重了」还是「插了串行验证」。前者正常，后者是该并行化的目标。
- **当场记摩擦**：在重活拍里 `friction log --stage act --kind wait --cost <分钟>`，让账本下次能自己说话，而不是靠回放反推。
- 并行验证集已写明命令，待权限放开后实跑并贴证据。
