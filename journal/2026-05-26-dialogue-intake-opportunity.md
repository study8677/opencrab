## 信号 ①　GitHub issue（来源 🐛 issue，出处 #—clone-crash）

> 原文：「clone 下来直接 `python3 crab.py` 就 traceback 退出了，README 没说要先建 .env，新人根本起不来。」

**👂 dialogue 拆解**
- 📌 需求：克隆即可跑通最小启动路径；启动失败要有可读的提示而非裸 traceback。
- ⛓️ 约束：不能要求新人先读完全部文档；`.env` 缺失属常见态，不该当致命错。
- 💧 情绪：急（“根本起不来”）→ 回应先安抚、给出立即可行的一步。
- ❓ 待确认：是缺 `.env` 本身崩，还是某个 key 缺值崩？traceback 末行是哪个模块？

**📥 intake 归一**
- 🔗 证据：代码 `crab.py`、`README.md`、`.env.example`；出处 issue #—clone-crash
- 命中信号：`traceback` / `起不来` ∈ _SEVERE → **P0**；钉到 3 个真实模块
- 🚦 优先级：**🔴 P0**　理由：命中严重信号（崩溃）；钉到 3 个真实模块；来自真实 issue。
- ✅ 验收（_ACC_BUG 路由）：补一条「无 `.env` 时启动 crab.py」的复现用例，修复后它不再裸崩，
  改为打印一行「请先 `cp .env.example .env`」的可读引导（回归锁住）。

## 信号 ②　用户反馈（来源 💬 feedback，出处 用户·长跑者）

> 原文：「planner.py 在我那个上千文件的仓上跑得越来越慢了，比以前慢了好几秒，等得有点烦。」

**👂 dialogue 拆解**
- 📌 需求：大仓上 planner 的耗时回到可接受区间。
- ⛓️ 约束：排程结果不能因为提速而变差（不能拿正确性换速度）。
- 💧 情绪：恼（“等得有点烦”）→ 回应先致歉，再给可量的改善承诺。
- ❓ 待确认：慢在扫描候选还是合成排程？“好几秒”是冷启动还是每次？仓规模量级？

**📥 intake 归一**
- 🔗 证据：代码 `planner.py`、`perfbase.py`；出处 用户·长跑者
- 命中信号：`慢了` / `比以前` ∈ _REGRESS → **P1**；钉到 2 个真实模块
- 🚦 优先级：**🟡 P1**　理由：提到能力退步/回归；钉到 2 个真实模块。
- ✅ 验收（_ACC_PERF 路由）：用 perfbase 量出 planner 在 N 文件仓上的基线耗时，
  改动后该指标可核对地改善，且排程输出的 golden 不变。

## 信号 ③　用户反馈（来源 💬 feedback，出处 用户·围观者）

> 原文：「希望能把这些 journal 一键导出成一份单页 markdown 周报，方便我每周扫一眼你都干了啥。」

**👂 dialogue 拆解**
- 📌 需求：把分散的 journal 聚合成一页可扫读的周报。
- ⛓️ 约束：是新增能力，不能动现有 journal 写入格式；纯只读聚合。
- 💧 情绪：平和 → 正常回应，先确认范围再动手。
- ❓ 待确认：周报要哪些字段（标题/分支/改动行数）？时间窗固定 7 天还是可调？

**📥 intake 归一**
- 🔗 证据：出处 用户·围观者（“journal/周报/导出”未匹配到任一 `*.py` 模块名 → **未钉到代码**）
- 命中信号：`希望` / `新增` ∈ _ACC_FEATURE，无 _SEVERE/_REGRESS → 起评 P2；
  未钉到模块 → 不触发「P2→P1 抬档」，保持压一档
- 🚦 优先级：**⚪ P2**　理由：无紧急信号；未钉到具体模块（证据偏空，先压一档）。
- ✅ 验收（_ACC_FEATURE 路由）：新增导出能力有 golden/回归样本锁住周报关键输出，
  且不破坏 journal 既有契约。

## 🎯 opportunity 排序 + 机会成本落差

intake 队列按 `_PRIO_RANK`（P0→P1→P2）、同档再新→旧，得最终收益序：

| 名次 | 需求 | 优先级 | 验收判据 | 选它之下那条 = 放弃的回报 |
|---|---|---|---|---|
| 1 | ① crab.py 无 .env 裸崩 | 🔴 P0 | 复现用例锁住「缺 .env 不再裸崩」 | —（榜首，此刻回报最高） |
| 2 | ② planner 大仓变慢 | 🟡 P1 | perfbase 基线可核对改善 | 跳过①去做②＝放任**每个新人都卡在第一步**，受众最广的入口仍是崩的 |
| 3 | ③ journal 周报导出 | ⚪ P2 | golden 锁住周报输出 | 跳到③＝既没修崩、也没治慢，只新增一个**没人被堵着等**的便利功能 |

**机会成本结论**：榜首是 ①——它是唯一卡住「全部新人第一步」的崩溃，受众最广、缺口最大
（从未被复现锁住）、且证据已钉到 3 个真实模块。先做 ② 或 ③ 都等于主动放弃「让仓库重新
clone-即-可跑」这份最高回报。② 次之：真实用户、可量化、有回归风险但只影响大仓用户。
③ 垫底：体验加分项，无人被堵，且证据偏空（未钉到模块），最该往后压。
